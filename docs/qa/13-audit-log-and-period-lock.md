# QA Ledger — Audit log and accounting period lock

Date: 2026-10-25 · Spec: `docs/superpowers/specs/2026-10-25-audit-log-and-period-lock-design.md` · Env: local QA DB, locale `ar`.

| ID | Sev | Finding | Status |
|----|-----|---------|--------|
| AL-01 | G | Nobody could tell who changed what, or when. | **done** — an **audit log** (System → Audit Log) lists every recorded change: who, when, which record, what event and the old and new values. It records creating, editing, archiving, restoring and deleting for the main business records (accounting documents, bank statements, journals, accounts, taxes, payroll, salary data, attendance, loans, employees, partners, companies, users and roles), plus sign-ins and failed sign-ins, changes of roles and permissions, changes of the lock date and every use of the lock override. Passwords and secrets are never shown: they appear only as "changed" with `***`. Only roles holding the audit permission see the screen (Admin, super_admin and general_manager after the sync); entries cannot be edited or deleted from the screen or from the application. Users with access to several companies see entries of those companies only. |
| AL-02 | G | Posted accounting entries could be edited, reset or deleted in any month by anyone with permission. | **done** — a **lock date per company** (Accounting → Configuration → Lock date; on a site without the Accounting plugin the page sits under Settings). Everything dated **on or before** the lock date is closed: posted invoices, bills, credit notes, refunds, payments, journal entries and bank statements in that period cannot be edited, reset to draft, cancelled, unlinked or deleted, and nothing can be posted into the period or moved into it. **Drafts are still allowed** in a closed period (they simply cannot be posted until the lock is moved back or an authorised user posts them). **Reconciliation and payment of old invoices still work**: an old invoice can be paid, or matched with a payment dated after the lock date, because that only changes the paid status and residual amounts. The lock date cannot be set later than today. Moving the date backwards unlocks the period; every change of the date is written to the audit log. A user holding the permission **"post in locked period"** can still post and change entries in a closed period; each such action is logged ("Locked period override"). With nobody signed in (scheduler, queue, console) the lock always applies and there is no override. A refused change shows "Period locked" naming the lock date. | **done** |
| AL-03 | note | **Limits of the audit log.** (a) It is not tamper-proof against someone with direct database access: a database administrator can still change or delete entries, so it records honest users' work, it is not forensic evidence. (b) Actions with no signed-in user (the scheduler, queued jobs, console commands, imports run from the command line) are **not logged**; only sign-in and failed sign-in are logged without a user. (c) **Nothing before this release is in the log**: history starts the day it is deployed. (d) Bulk work such as generating a payroll batch creates **one entry per payslip line**, so a batch of hundreds of lines adds hundreds of entries at once; the screen paginates, but expect the table to grow quickly. (e) Entries not tied to a company (sign-ins, role and permission changes) are visible to **everyone who holds the audit permission**, whatever company they work in. (f) The search box searches the **changed values only** (old and new text), not the record's name or the user's name; use the filters (user, record type, event, date) for those. (g) Sign-in entries are written for **web logins**; logins through API tokens are not recorded. | by design |
| AL-04 | note | **What the lock does not cover.** Only accounting documents are locked (journal entries and their lines, invoices, bills, credit notes, refunds, payments, bank statements and their lines). **Payroll batches and payslips, inventory moves and stock valuation are not locked** (payroll has its own validated/paid states). There is **no separate VAT/tax lock date**, and **no fiscal-year closing entries** (no year-end close that carries balances forward). A lock date is per company: set it for each company separately. Changes written directly to the database, or by code that bypasses model events (for example `saveQuietly`), also bypass the lock and the audit log. | by design |
| AL-05 | note | **Refusals to expect while a period is locked (existing plugin behaviour, now visible).** (a) **Resetting to draft, unlinking a payment from, or reversing the payment of an invoice dated in a locked period is refused**: those actions delete and recreate the invoice's receivable/payable line, which is a change to a locked entry. Move the lock date back (or use the override permission) to do it. (b) **Reversing a locked invoice (credit note) is refused**: the existing "Reverse" action ignores the date chosen in the dialog and dates the credit note on the **original** invoice date, which is inside the locked period. The workaround is to create the credit note manually with a date after the lock date. This is a plugin bug and was not changed. (c) **Multi-currency exchange-difference entries were not exercised**; if the plugin dates one inside a locked period it will be refused. (d) A refused action rolls back completely: partial work is not left behind (the invoice actions, the payment actions, invoice-summary "Unlink"/"Reconcile" and the accounting API writes run in a transaction). Direct programmatic use of the accounting facade outside these paths is the caller's responsibility. | by design |
| AL-06 | action | **Finance must set the date after each close, and move it forward.** Nothing locks automatically. After closing a month, the accountant must open Lock date and set it to the last day of that month. Until someone sets it a company is completely unlocked (a company with no lock date behaves exactly as before). | **action (every close)** |
| AL-07 | note | **Deploy notes.** Queue workers re-read the lock date at the start of every job, so nothing needs to be restarted when the date changes. Writes through the accounting REST API (`/admin/api/v1/accounts/...`) are now **atomic**: a request that ends in an error answer (4xx/5xx) is rolled back as a whole, including payment and reconcile steps done before the error. | **done** |
| AL-08 | note | Test infrastructure: after pulling the new migrations run `php artisan migrate --env=testing` (adds `companies.accounting_lock_date` to the test database). | open (test hygiene) |

## Rollout on an existing site
1. `php artisan migrate --force` (adds the lock date column; every company starts unlocked, so nothing changes until step 4).
2. `php artisan permissions:sync-extensions` — creates and grants the audit permissions (`view_any_filament_audit::log`, `view_filament_audit::log` to Admin, super_admin, general_manager) and the lock permissions (`page_filament_manage_lock_date` and `post_in_locked_period` to Admin, super_admin, finance_manager).
3. If other roles should read the audit log or manage the lock date, grant "View Any / View Audit Log" or the "Manage Lock Date" page permission to them in the Roles screen.
4. For each company, open Accounting → Configuration → **Lock date** and set it once (normally the end of the last closed month). Choose the company at the top; the saved date for that company is shown.
5. Give the accountant role **"post in locked period"** deliberately, only to the people who must correct closed periods. The permission appears in the Roles screen (Advanced permissions, Custom tab) from this release, and a role keeps it when the box stays ticked while the role is saved; untick it there to withdraw it. Tell them that every use is recorded in the audit log under their name.
6. Tell finance to move the date forward after every close (AL-06), and that an old invoice can still be paid while its period is closed (AL-02).
